# Portfolio Manager Project Plan

## 1. 项目目标

四人团队分阶段交付一个投资组合管理应用：

1. 完成持仓的查询、新增、删除和MySQL持久化。
2. 增加购买历史、当前行情和Performance分析。
3. 完成前后端集成、自动化测试、Docker开发环境和项目演示。

项目以[`user-stories.md`](./user-stories.md)中的US-01至US-07作为范围依据。

## 2. 团队角色

| 角色 | 主要负责范围 | 次要责任 |
|---|---|---|
| 后端A | US-01、US-02、US-03 | Portfolio核心模型、CRUD接口、统一错误格式 |
| 后端B | US-04、US-05 | MySQL持久化、Docker数据卷、购买历史 |
| 后端C | US-06、US-07 | 行情服务、汇率转换、Performance计算 |
| 前端 | US-01至US-07的页面和交互 | API联调、图表、错误和加载状态 |

所有成员共同负责：

- 需求确认和API契约评审。
- Pull Request代码审查。
- 自己负责功能的自动化测试。
- 交叉验收、回归测试和缺陷管理。
- 每日短会和风险同步。
- README和最终演示。

## 3. 开发前必须统一的设计

在分头开发前，四人需要先确认以下内容，避免后期接口无法集成：

### 3.1 数据职责

```text
portfolio_items
    表示用户当前持有多少资产

transactions
    表示历史上发生过哪些BUY或SELL交易
```

购买历史必须独立保存。删除当前持仓不能连带删除历史交易。

### 3.2 核心数据模型

```text
PortfolioItem
- id
- assetType
- symbol
- quantity

Transaction
- id
- transactionType
- assetType
- symbol
- quantity
- pricePerUnit
- currency
- purchasedAt
```

### 3.3 第一版业务约定

- 第一版只支持单一基础货币，例如USD。
- 股票代码保存前统一去除空格并转换成大写。
- 金额和收益率统一使用`BigDecimal`。
- 时间统一通过ISO 8601格式传输，并以UTC保存。
- 外部行情缺失时返回`PARTIAL`，不能把价格当作0。
- US-02的“添加持仓”和US-05的“记录购买”需要在第二阶段统一，避免当前持仓与交易历史不一致。

### 3.4 API契约

```http
GET    /api/portfolio/items
POST   /api/portfolio/items
DELETE /api/portfolio/items/{id}

POST   /api/transactions
GET    /api/transactions?type=BUY

GET    /api/portfolio/value
GET    /api/portfolio/performance
```

前后端开发前应共同确认每个接口的请求、响应、状态码和错误格式。

## 4. 实施阶段

项目总开发时间为3天。四人必须并行开发，每天结束前合并一次可运行版本，不能等到最后一天才进行前后端联调。

### 三天范围优先级

| 优先级 | 必须交付 |
|---|---|
| P0 | US-01至US-05、MySQL持久化、Docker启动、基础前端 |
| P1 | US-06当前价格和当前价值 |
| P2 | US-07基础Performance：成本、当前价值、盈亏和收益率 |

三天内不做或仅在全部核心功能完成后再做：

- 历史收益折线图。
- 多币种组合汇总。
- SELL交易和复杂成本法。
- 用户认证。
- AI或量子功能。
- 复杂动画和页面美化。

US-07仍然属于目标范围，但首先交付数字摘要；资产占比饼图有时间再完成。

## 6. 关键依赖关系

```text
US-01/02/03/04：持仓MVP
          │
          ├──────────────┐
          ▼              ▼
US-05：购买历史     US-06：当前行情和价值
          │              │
          └──────┬───────┘
                 ▼
        US-07：Performance分析
                 │
                 ▼
          前端图表和最终展示
```

US-07不能在US-05和US-06之前完成，因为：

- 没有购买历史就没有可靠的成本基础。
- 没有当前行情就不能计算当前价值。
- 没有成本和当前价值就不能计算盈亏与收益率。

## 7. Git和Pull Request计划

建议分支：

```text
feature/us01-list-portfolio
feature/us02-add-asset
feature/us03-delete-asset
feature/us04-persistence
feature/us05-purchase-history
feature/us06-current-value
feature/us07-performance
feature/frontend-portfolio
test/cross-acceptance
```

Pull Request要求：

- 一个PR尽量只对应一条User Story。
- PR描述中链接对应GitHub Issue。
- 至少由另一位成员审核。
- 三名后端采用循环审核：后端B审核A、后端C审核B、后端A审核C。
- 涉及共享实体或DTO的PR至少需要两个后端成员确认。
- CI通过后才能合并。
- 不直接向`main`推送功能代码。

## 8. 测试策略

| 测试类型 | 重点 | 主要负责人 |
|---|---|---|
| 单元测试 | Service计算、校验、异常 | 各功能后端负责人 |
| Repository测试 | MySQL/JPA查询和排序 | 后端A、后端B |
| 行情Client测试 | 成功、超时、失败和部分数据 | 后端C |
| API测试 | 状态码、JSON、错误响应 | 对应交叉验收人 |
| 前端组件测试 | 表单、列表、图表状态 | 前端 |
| 端到端测试 | 添加、查询、历史、Performance | 前端主导、三名后端支持 |
| 完整回归 | US-01至US-07 | 四人共同执行 |

项目没有专职测试人员，因此每项功能必须“开发者写自动化测试、另一名后端做交叉验收”。测试不能集中到最后，应在每个PR合并前完成。

## 9. 主要风险和应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 持仓与交易历史不一致 | Performance计算错误 | 阶段0确定唯一更新流程，并使用事务 |
| Yahoo行情不可用或受限 | US-06、US-07阻塞 | 抽象行情接口，提供固定价格Stub |
| 三名后端同时修改共享模型 | 合并冲突 | 先冻结DTO和实体字段，小PR频繁合并 |
| 前端等待后端 | 进度阻塞 | 阶段0提供模拟JSON和API契约 |
| 金额使用浮点数 | 计算误差 | 全部使用`BigDecimal`和统一舍入规则 |
| 删除持仓时删除历史 | 历史丢失 | Transaction不配置级联删除 |
| 没有专职测试人员 | 测试被开发任务挤占 | 每个Issue包含测试任务，并采用循环交叉验收 |

## 10. 项目完成定义

项目完成需要同时满足：

- US-01至US-07验收标准通过。
- 前端能够完成所有核心用户操作。
- MySQL数据可以持久化。
- Performance计算由独立测试数据验证。
- 行情不可用时系统能够降级。
- Docker全栈能够启动。
- GitHub CI通过。
- 没有未处理的高优先级缺陷。
- README、API文档和演示步骤完整。
